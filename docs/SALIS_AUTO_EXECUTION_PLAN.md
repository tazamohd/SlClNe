# SALIS AUTO — Master Rebuild & Production Execution Plan

> Written against the **MASTER REBUILD & PRODUCTION EXECUTION PROMPT** (§0–§64).
> `§n` below refers to that document. Where two revisions of the prompt differ
> (registry schema, breakpoints, website page list), this plan implements the
> **union** of both.

---

## Context

`app/` is a production React rebuild of the Claude Design handoff in `project/`.
**113 of 402 routed screens are built**; the other **289 render `PendingScreen`**,
which §60 forbids outright. Everything is mock-backed — no server, no database,
no persistence, no real auth, no tests beyond a Playwright smoke script, no CI.
Typecheck, build and smoke are green; §5 is explicit that this is a *baseline*,
not proof of completeness, so this plan re-verifies rather than inherits.

The objective is not "all routes exist" but a **complete, coherent, responsive,
secure, tested, production-ready product** (§63).

**Source-of-truth hierarchy** (§3), applied throughout:

1. `project/*.dc.html` + `project/spec-shots/` — visual, layout, interaction
2. `project/spec/` — which capabilities exist (235 screens)
3. `app/src/` — existing behaviour, data shapes, empty states
4. `handoff/DATA_MODEL.md`, `RBAC.md`, `API_ENDPOINTS.md`, `FLOW_SPEC.md` —
   business and data authority

Nothing is invented where the sources are silent; ambiguity is recorded as an
assumption in the registry rather than resolved by fabrication (§3, §63).

# Part 2 — Foundations that govern everything

## 2.1 Master completion registry (§4)

`app/scripts/build-registry.mjs` merges `SCREEN_MAP.md`, `project/spec/`, the
`.dc.html` inventory and an authored overlay into
**`src/data/generated/master-registry.ts`**, rendering
**`docs/SALIS_AUTO_MASTER_MATRIX.md`**.

Fields are exactly those §4 requires:

```ts
export interface RegistryEntry {
  id: string; name: string; module: string
  surface: 'erp'|'portal'|'customer-app'|'public'|'auth'|'kiosk'|'native'|'reference'
  route: string
  shell: 'AppShell'|'AuthShell'|'CustomerAppShell'|'PublicShell'|'PortalShell'|'KioskShell'
  desktop: Cov; tablet: Cov; mobile: Cov
  designedDesktop: string | null      // project/X.dc.html
  designedMobile:  string | null      // project/X.Mobile.dc.html
  arabic: Cov; rtl: Cov
  dataBacked: boolean
  crud: { create: boolean; read: boolean; update: boolean; delete: boolean }
  rbac: string[]                      // roles × actions from RBAC.md
  api: string[]                       // endpoints from API_ENDPOINTS.md
  audit: boolean; notifications: boolean; files: boolean; print: boolean
  accessibility: Cov
  e2e: boolean; visualTest: boolean; performanceTest: boolean; securityTest: boolean
  status:
    | 'DISCOVERED' | 'PLANNED' | 'IN_PROGRESS' | 'IMPLEMENTED' | 'DATA_BACKED'
    | 'TESTED' | 'VISUAL_VERIFIED' | 'PRODUCTION_READY'
    | 'BLOCKED' | 'REFERENCE_ONLY' | 'DEPRECATED' | 'REDIRECT'
  blockers: string[]                  // incl. EXTERNAL_DEPENDENCY notes (§60)
  source: string[]                    // dc.html, spec id, screenshot, assumptions
}
type Cov = 'MISSING' | 'PARTIAL' | 'DONE' | 'VERIFIED' | 'N/A'
```

**Everything downstream is generated from this registry, never hand-maintained**
(§4, §47): the route table, nav, route/E2E coverage checks at every breakpoint,
RTL and a11y sweeps, the visual-regression baseline list, the completion matrix,
the §61 final report and the §62 release score.

**Fake-completion gate** (§60): `scripts/check-no-fake.mjs` fails the build when
a non-`REFERENCE_ONLY` / non-`EXTERNAL_DEPENDENCY` / non-`NOT_IN_SCOPE` entry
renders `PendingScreen`, or when `TODO` / `Coming soon` / `Not implemented` /
`placeholder` / `onClick={() => {}}` / `console.log` appear in `src/screens/**`
or `server/src/**`. `PendingScreen` is deleted once Part 3 completes.

## 2.2 Real data / API architecture (§34–§36)

```text
UI → Hooks → Repository → API Client → Auth → Authz → Backend → Database
```

| Layer | Choice | Why |
|---|---|---|
| Runtime | Node 20 + **Fastify** + TS, in `server/` | Same language as the client; schema-first |
| Database | **PostgreSQL 16** + **Row-Level Security** | `handoff/README.md` §2 recommends RLS for per-row data scope |
| ORM / migrations | **Drizzle** (`server/src/db/schema.ts`, `drizzle/`) | Typed SQL, plain migrations |
| Validation | **Zod** in `packages/contract/`, shared client↔server | One schema = API type + server guard + form validator |
| Auth | JWT access 15 min + rotating refresh 30 d with reuse detection; argon2id | `API_ENDPOINTS.md` claims `{sub, role, org_id, branch_id, scope}` |
| Authz | `requirePermission(module, action)`, `requireApproval(amount)`, SOD guard — mirroring `src/data/rbac.ts` | §36 |
| Tenancy | `org_id`/`branch_id` on every table; RLS via `SET LOCAL app.org_id` | Isolation the client cannot bypass |
| Files | S3-compatible behind `StorageAdapter`; MinIO in dev | §37 |
| Jobs | pg-boss — notifications, reminders, report generation, retries | §38 |
| Realtime | SSE for notifications and job status | `API_ENDPOINTS.md` §WebSockets |
| Observability | Structured JSON logs with PII redaction, Sentry, `/health`, `/ready` | §52 |

**Data model** — the 35 mock tables + `DATA_MODEL.md`'s "to be designed"
entities (`organizations`, `branches`, `tenants`, `user_sessions`,
`PurchaseOrders`) + the platform control plane (`garage_applications`,
`subscription_requests`, `supplier_applications`, `support_tickets`,
`system_health`, `otp_challenges`, `audit_log`). Universal fields per
`DATA_MODEL.md` §1. **Money stored as integer halalas**, formatted at the
boundary — the client's `formatSar` is unchanged.

**Seed = today's mocks.** `server/scripts/seed.ts` imports
`src/data/generated/tables.ts`, so the seeded database renders exactly what the
app renders now and **every existing smoke assertion must still pass after the
swap** — that is how the mock → HTTP migration is proven non-destructive (§57).

**Repository interface** (§34), replacing today's read-only seam:

```ts
export interface Collection<T> {
  list(q?: Query): Promise<Paged<T>>            // page, sort, filter, search
  get(id: string): Promise<T>
  create(input: Partial<T>, o?: Opts): Promise<T>
  update(id: string, patch: Partial<T>, o?: Opts): Promise<T>   // o.version → 409
  delete(id: string): Promise<void>
  bulkCreate(inputs: Partial<T>[]): Promise<T[]>
  bulkUpdate(ids: string[], patch: Partial<T>): Promise<T[]>
  bulkDelete(ids: string[]): Promise<void>
}
```

`useCollection.ts` gains `useEntity`, `useCreate`, `useUpdate`, `useDelete`,
`useBulk` with caching, invalidation, optimistic updates, rollback and
optimistic-concurrency conflict handling — so no persistence logic ever lands in
a visual component. Screens stay coupled to the repository, never to the backend.

## 2.3 Foundation UI system (§6–§10)

**Primitives** (§6) — build or finish: `Modal`, `Drawer`, `Dialog`, `Toast`✓,
`Alert`, `Tooltip`, `Popover`, `Tabs`, `Accordion`, `DataTable`✓, `MobileCard`✓,
`Pagination`, `Search`, `AdvancedFilters`, `CalendarView`, `KanbanView`,
`ActivityFeed`, `Comments`, `Attachments`, `MediaGallery`, `MapView`, `Charts`,
`ImportCenter`, `ExportCenter`. Extract from existing screens rather than
copying: `Charts` out of `accounting/Reports.tsx`, `KanbanView` out of
`LeadPipeline`, `AdvancedFilters` out of the three duplicated chip
implementations.

**Universal state system** (§7) — `LoadingState`, `Skeleton`, `EmptyState`,
`ErrorState`, `RetryState`, `PermissionDenied`, `NotFound`, `OfflineState`,
`SavingState`, `SuccessState`, `UnsavedChanges`, wired as props on
`ListPage`/`DetailPage` so no screen can ship an unexplained blank area.

**Form system** (§8) — `Form`/`Field`/`useZodForm` over the shared contract
schemas: validation, field errors, server errors, async validation, dirty state,
unsaved-changes guard, draft, reset, submit, loading, rollback. Fields: Text,
Textarea, Email, Phone, Currency, Percentage, Date, DateRange, Select,
SearchSelect, MultiSelect, VIN, VAT, File, Signature — each with Arabic,
English, RTL, keyboard navigation, accessible labels and validation messages.

**Modal system** (§9) — six families (CRUD, Lifecycle, Status, Actions, Data,
Capture) with focus trap, Escape, focus restoration, scroll lock, portal,
`role="dialog"`, `aria-modal`, RTL-safe logical CSS, async submission,
validation, server errors, and **full-screen sheet on mobile / centred dialog on
desktop**. Exposed as `ModalProvider` + `useModal()`, following the existing
`ToastProvider` pattern. **All 23 dead CTAs are wired to it in the same tranche.**

**Shells** (§10) — add `PublicShell`, `PortalShell`, `KioskShell`; extend
`RequireAccess`'s `shell` union; every route declares its shell **in the
registry**, and a generated test asserts each route renders inside the declared
shell.

**Detail page architecture** — `components/shell/DetailPage.tsx`: header, status,
primary actions, metadata, tabs, summary, details, related records, timeline,
comments, attachments, activity rail, audit. Used by all nine detail screens.
`fieldHidden()` is applied only after proving reachability against RBAC.

**Business rule engine** (§42) — rules live in `packages/contract/rules/`, not in
components: invoice totals, VAT, discount, rounding, approval limits, SOD,
inventory, reservations, job states, payment allocation, credit, refund. Each is
unit-tested independently and enforced server-side.

**Design-token drift detection** — `scripts/check-tokens.mjs` parses `src/**` for
hardcoded colours, spacing, radii, shadows and typography outside the token set
and fails CI on drift. This subsumes and extends the existing brand guard, which
already walks computed styles for forbidden green/purple across sample routes and
will be extended to the full route inventory.

# Part 4 — Reporting, search, files, notifications, documents

- **Reports** (§24) — every report screen supports filters, date range,
  organization, branch, search, charts, tables, export (CSV/Excel), print, PDF,
  plus loading/empty/error, mobile, Arabic and RTL. Aggregates come from the
  API, never from client-side arithmetic over a page of rows.
- **Global search** (§39) — permission-aware across customers, vehicles, job
  cards, invoices, parts, suppliers, appointments, leads, employees, documents;
  Arabic and English; VIN, phone and invoice-number matching; fuzzy where
  appropriate; results filtered server-side by role and tenant.
- **File platform** (§37) — upload, MIME and size validation, storage, preview,
  download, delete, attach/detach, versioning, permissions, audit, virus
  scanning at the boundary.
- **Notifications** (§38) — in-app, email, SMS, push behind one abstraction, with
  templates in both languages, per-user preferences, delivery status, retry,
  read/unread, deep links and audit.
- **Print / PDF** (§41) — invoice, estimate, job card, purchase order, receipt,
  statement, report, insurance and loan documents; A4, print and PDF, English
  and Arabic with correct RTL composition; rendered server-side.

# Part 5b — Business invariants, journeys and data integrity

## Business invariants — encoded once, tested individually

Enforced server-side, surfaced as form validation, each with its own unit test.
A violated invariant fails CI.

```text
Invoice.total = subtotal + tax − discount
Payment.amount ≤ invoice.balance
Cancelled invoice cannot receive a normal payment
Refund ≤ amount collected
ReservedStock ≤ AvailableStock; consumption ≤ reservation
Completed JobCard required before invoicing
QC pass required before delivery
Expired Estimate cannot be approved
Estimate above the role ceiling must escalate (canApprove)
SOD pair: the performer cannot be the QC approver
Purchase order cannot exceed the approval ceiling
Receiving quantity ≤ ordered quantity (over-receipt needs approval)
Journal entry debits = credits
VAT computed at the ZATCA rate, never stored client-side
User cannot cross an organization boundary
Branch-scoped user cannot reach another branch; 'own' scope sees only own records
Appointment cannot double-book a bay
Payroll period cannot be reopened after posting
```

The list grows as further rules are found in the repository, rather than being
treated as closed.

## Golden user journeys — 30–50, run against the real application

The certification journey is one spec end to end:

```text
NEW CUSTOMER → VEHICLE → APPOINTMENT → CHECK-IN → INSPECTION → JOB CARD →
DIAGNOSIS → ESTIMATE → APPROVAL → PARTS → REPAIR → QC → INVOICE → PAYMENT →
RECEIPT → HISTORY
```

Each of the following is its own spec, run desktop + 390 px + Arabic/RTL:
customer mobile booking · customer mobile estimate approval · customer portal
invoice payment · technician mobile job completion · technician time tracking ·
supplier order fulfilment · requisition → PO → receiving → inventory · parts
network RFQ → quotation → order · inventory reservation → consumption → reorder ·
lead → opportunity → customer · campaign → segment → send · insurance claim
lifecycle · loan lifecycle · fleet contract lifecycle · invitation → onboarding →
RBAC initialisation · branch creation → employee assignment · accounting →
reconciliation → statement · report → export (CSV/PDF) · call-centre lookup →
booking → follow-up · kiosk identify → check-in → confirmation · admin role

public site → request demo → lead in CRM · notification → deep link → action ·
global search → record → action · session expiry → re-auth → resume · offline →
retry → no duplicate.

## Data-integrity audits

- **No-orphan audit** — scripted checks that
  Customer→Vehicle→Appointment→Job→Estimate→Invoice→Payment and
  Supplier→PurchaseOrder→Receiving→Inventory contain no orphan relationships, run
  against the seed and after every journey suite.
- **Data-quality audit** — duplicates, invalid relationships, impossible values,
  missing required fields, inconsistent statuses, invalid dates, invalid monetary
  values, broken foreign keys. Bad data is **reported, never hidden to make the
  UI look correct**.

## Chaos, recovery and AI evaluation

- **Chaos** — API timeout, database timeout, network disconnect, payment / SMS /
  email / storage failure, duplicate webhook, expired session, slow API, partial
  response. The application must degrade gracefully, never silently.
- **Recovery** — network lost → operation fails → retry → success → **no
  duplicate data**, proven against the idempotency keys; plus a real
  backup-and-restore drill, not a documented intention.
- **AI evaluation** — an eval harness measuring accuracy, grounding,
  hallucination, data leakage, permission boundaries, Arabic/English/RTL output,
  incorrect calculations, unsafe requests, prompt injection and conflicting
  instructions. AI quality is measured, not assumed, and consequential actions
  follow: suggestion → validation → permission → human confirmation → execution →
  audit.

## Demo mode

Deterministic demo data lives in an isolated `demo` organization, seeded
separately and never able to mutate production records. Feature lifecycle
(`PROPOSED → DEVELOPMENT → INTERNAL_QA → STAGING → BETA → PRODUCTION →
DEPRECATED → REMOVED`) maps onto the registry's `status` field, so a screen's
maturity is data, not commentary.

# Part 7 — Security (§36, §50, §56)

- Server-side `requirePermission` on **every** route; a generated test asserts
  the client `PERMS` matrix and the server matrix are identical.
- Postgres RLS enforcing `all` / `branch` / `own` scope per `RBAC.md`, across
  organization, branch, user, role, permission, record and field levels.
- Approval ceilings and SOD pairs enforced server-side; client checks remain UX.
- **Permission simulation suite**: 14 personas × {navigate, view, create, edit,
  delete, approve, export, download, assign, manage} × 28 modules, driven
  against the real app and the real API, reporting ALLOWED / DENIED /
  **UNEXPECTED ACCESS**. Any unexpected access is a release blocker.
- IDOR tests on every `:id` route; cross-tenant reads return **404, not 403**.
- Auth lifecycle (§35): login, register, email verification, password reset,
  invitation, SSO, social, session, refresh, expiry, logout, revocation — with
  explicit handling for expired session, invalid session, failed refresh,
  revoked account, failed login and invitation expiry.
- XSS, CSRF, injection, file-upload, path-traversal, rate-limit and
  security-header tests; secret scanning (gitleaks) and dependency scanning in CI.
- Structured logs with PII redaction (§52); immutable `audit_log` for every
  mutation, approval and permission denial.
- **Rotate the three exposed GitHub PATs**; decide whether the repo stays public.
