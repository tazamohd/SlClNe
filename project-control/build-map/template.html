Delivery model

Six waves, and one of them holds up everything else

Ten product agents cannot start until four foundation agents finish. That single edge — W1 → W2 — is the whole schedule. Shortening W1 shortens the project; nothing else does.

In plain words: you can't build rooms before the foundation is poured. Ten builders stand idle while four pour it, so the fastest thing you can do is put more people on the foundation.

Architecture

Every screen talks to a seam, so the backend can land without moving one of them

Screens never call the network. They call a Collection<T> repository. Today that repository reads fixtures; tomorrow the same interface is implemented over HTTP and selected by an environment variable. The database is seeded from the very fixtures the app renders now — so every assertion that passes today must still pass after the swap. A failure means the swap is wrong, not the test.

In plain words: the app is wired to a socket, not to a wire. You can swap what's behind the socket — fake data for a real database — and none of the 403 screens notice.

Security

The client gate is a courtesy. The wall is on the server.

14 roles × 28 modules × 5 actions is a matrix the app enforces in the browser — which is convenience, not security. Every sensitive operation has to re-validate identity, organization, branch, role, permission, resource ownership and the business rule on the server. Bypassing the UI must still be denied. A cross-tenant read returns 404, never 403 — a 403 confirms the record exists.

In plain words: hiding a button doesn't stop anyone. The check that matters happens after the request leaves the browser, where the user can't touch it.

The documents disagree — and that is the system working

The registry snapshot above is dated 21 Aug 2026 and reports 0 data-backed capabilities. The release plan's progress note, dated 12 Aug 2026, describes a landed backend — schema, RLS, JWT auth, server-side RBAC, audit, concurrency, idempotency — with 155 routes on real connected screens and 971 tests passing.

Both can't be the current truth. The plan's own rule settles it: a count written into a document is a dated snapshot, not a fact — the registry is the fact. The right move is to re-run npm run gates and read the regenerated numbers, not to reconcile two prose paragraphs. This is precisely the failure mode the registry exists to make visible.

The short version

What to hold on to

Six things this build gets right, and one thing that decides the schedule

  • Nothing is counted by hand. Route tables, tests, gates, matrices and reports all fall out of one generated registry. A hardcoded total is treated as a defect.
  • The unit of completion is a capability, not a file. "Customer management" can be done; Customers.tsx cannot.
  • No agent certifies its own work. An agent may mark its own work DONE; only the release manager sets VERIFIED, and only after re-running the checks.
  • The seam is what makes the backend swap safe. The database seeds from today's fixtures, so every assertion that passes now must still pass after the swap.
  • The client gate is a courtesy. The real boundary is server-side, and a cross-tenant read returns 404 rather than confirming the record exists.
  • Rendering is the floor. 363 of 403 screens draw; zero are backed by real data, tablet-verified, or production-ready. Both facts are true at once, and the second one is the honest one.
  • W1 decides the calendar. Ten product agents wait on four foundation agents, and the backend does not parallelise. Shortening the foundation is the only lever on elapsed time — everything else is effort, not schedule.
