The snapshot chain is frozen — the next generated migration cannot apply

Critical fixed

Repaired, on the second attempt. The previous revision of this report marked this finding fixed and named files — 0011_snapshot.json, 0011_snapshot_realign.sql — that were in no commit. The repair had been done in a working tree and never committed, so the defect stayed live for anyone who cloned the repository.

It is now committed as drizzle/meta/0012_snapshot.json (the true 68-table state) and drizzle/0012_snapshot_realign.sql (deliberately empty, reasoning in its header). Verified on a scratch PostgreSQL 16 cluster: drizzle-kit generate answers “No schema changes, nothing to migrate” and writes no file; the migration applies to an already-migrated database as a clean no-op at 68 tables; and the whole chain 0000–0012 runs on an empty database to 68 tables. Schema work is unblocked.

drizzle/meta/ held two snapshots against twelve journal entries, and both files were 186,405 bytes — a deep diff showed they differed in exactly two fields, id and prevId. The second is a hand-copied stub, so the recorded state had not moved since 0000_init: it still described 51 tables while the migrations had grown the schema to 68.

Nothing errored, which is why it survived eleven migrations. drizzle-kit generate silently diffed schema.ts against that stale base and emitted 492 lines: 17 CREATE TABLE, 26 CREATE INDEX and 17 ALTER TABLE … ADD COLUMN. The tables, indexes and foreign keys carry IF NOT EXISTS or a duplicate_object guard. The seventeen ADD COLUMNs carry nothing, and drizzle wraps all pending migrations in one transaction, so the first 42701 duplicate_column aborts the whole run. No schema change could be added to this project until it was repaired.

No real drift underneath it, and that was checked rather than inferred. parts.cost_halalas is the one nullable money column

High verified

It sits directly beneath price_halalas bigint DEFAULT 0 NOT NULL and carries no constraint of its own. Across all 68 tables it is the only money column that permits NULL.

SUM and AVG skip NULLs silently. An inventory valuation over 100 parts with 10 nulls returns the total for 90 and presents it as the total — no error, no zero, just a quietly low number that reconciles against nothing. This is the failure mode that costs the most to find later, because nothing about it looks wrong.

Money and quantity columns carry no range constraint

Medium

Roughly a dozen *_halalas columns are correctly NOT NULL DEFAULT 0 but have no CHECK (… >= 0). estimate_lines.qty and invoice_lines.qty are double precision NOT NULL with no CHECK (qty > 0).

A sign error writes a negative that sums cleanly and reconciles to the wrong figure. A zero or negative quantity flows through computeInvoiceTotals and produces a plausible-looking wrong subtotal. Status columns are likewise unconstrained varchar holding semantic enums — the database will accept any string the application forgets to validate.

Tenant context cannot leak across the pool

All four GUCs are set with set_config(…, true) — transaction-local, reverted at commit. 32 call sites across src/, scripts/ and tests/, every one local; zero session-local, zero bare SET. Connection reuse at pool size 10 has nothing to carry.

Policies fail closed

nullif(current_setting('app.org_id', true), '') yields NULL when unset, and a row-security predicate admits only on TRUE. An unset context returns zero rows, never another tenant's.

The four RLS-exempt tables hold no tenant data

garage_applications and supplier_applications are pre-tenant onboarding; system_health is platform telemetry; otp_challenges precedes authentication. None has an org_id to anchor a policy to.

No superuser is required

No CREATE EXTENSION, ALTER SYSTEM, event triggers or SECURITY DEFINER anywhere. IDs are ULIDs minted in JS. A plain owner role with CREATEROLE suffices.

Money and time are modelled correctly

Every amount is bigint halalas — no float money anywhere. Every timestamp is timestamptz, so container-UTC versus Windows-local changes nothing.

Migrations are idempotent

CREATE TABLE IF NOT EXISTS throughout; constraints wrapped in DO $$ … EXCEPTION WHEN duplicate_object; policies dropped before recreation. The hand-written chain is disciplined.

Previously outstanding all five resolved

This report used to close with five failing tests, described as contradictions between the application and its own suite. All five have since been settled in the codebase, and the server suite runs 30 files / 2,473 tests green. They are kept here because how each was settled is the useful part.

Helmet was configured more loosely than the tests demanded

4 tests resolved

Settled in the direction the suite asked for rather than by relaxing the assertions: src/app.ts now registers helmet with useDefaults: false, a CSP of default-src 'none', and frameguard: { action: 'deny' }. The rate limiter emits the RateLimit-* headers, and CORS exposes them.

The report was right that this was a posture decision, not a bug. The decision was to take the stricter posture — weakening a security control to make a test pass is the wrong direction of fit.

An unknown path answered 401 where the test wanted 404

1 test resolved

Resolved along with the wider 400-versus-422 question: a body that does not match the schema is a 400 bad_request; a schema-valid body refused by a domain rule is a 422 rule_violated. The 401-before-routing behaviour was kept deliberately — a 404 tells an unauthenticated caller which paths exist.

Two suites signed in with a password the seed never sets

2 suites resolved

Fixed in the tests, as the report recommended, not by seeding a credential into the repository: collections and writes now establish their own principal at setup. The seed's rule stands — “a seeded password hash in a repository is a credential in a repository.”

How it was brought up no Docker, no admin rights

Docker Desktop turned out to be wedged — pipes accepting connections with no engine behind them, its WSL2 VM stopped, dockerd absent, and docker desktop restart timing out past four minutes. The postgres superuser password on the existing 5432 install was also lost. Neither mattered in the end: initdb creates a cluster as an ordinary user, so a second cluster was built on port 5433 whose superuser we set ourselves. The 5432 service was never touched.

  1. Create a cluster we own, from the binaries already installed. 
    initdb -D %LOCALAPPDATA%\salis-auto-pg\data -U postgres \
  --pwfile=… --auth-host=scram-sha-256 --encoding=UTF8 --locale=C

    No administrator rights and no service registration — initdb runs as an ordinary user, and creating the cluster is what makes its superuser password ours to set.

  2. Pin it to port 5433, loopback only. 
    port = 5433
listen_addresses = 'localhost'

    Appended to postgresql.conf before first start, so it can never collide with the 5432 service and is not reachable off the machine.

  3. Create the owner role explicitly. 
    CREATE ROLE salis_admin LOGIN PASSWORD '…' CREATEROLE CREATEDB;
CREATE DATABASE salis_auto OWNER salis_admin;
GRANT pg_signal_backend TO salis_admin;

    Verified after creation: salis_admin is rolsuper=false, rolbypassrls=false. That matters — a superuser bypasses RLS even under FORCE, so migrating as one would make the isolation suite pass vacuously. server/.env.example suggests exactly that for DATABASE_ADMIN_URL, which is a trap worth correcting in the committed file.

  4. Migrate and seed, then check the result against the audit's predictions.

    Every prediction held: 68 tables matching schema.ts, RLS enabled and forced on 64, 128 policies, salis_app created non-superuser, and the four RLS-exempt tables exactly the four named in this report.

  5. Repair the snapshot chain, now that a live database proves the target state.

    Regenerated against the migrated database, kept the corrected snapshot, emptied the SQL. generate now answers "No schema changes".

RLS caught the author of this report out, which is a good sign. A plain select count(*) from users as salis_admin returned 0 — and the table has 15 rows. With no tenant GUC set, the policy evaluated to NULL and correctly returned nothing. The rows only appear once app.scope is set to platform. Fail-closed, exactly as designed, demonstrated by accident.
