Security enforced by the database, not just by convention

Every claim on this page describes a mechanism that exists in the system today — not a policy statement or a certification we haven't earned.

Tenant isolation

A workshop's data cannot leak to another tenant

Row-level security, fails closed

Every table is governed by a row-level-security policy scoped to the organization. A database connection with no request context reads nothing — the default is to see nothing, not everything.

FORCEd, even for the table owner

The policy applies even to the database role that owns the table, so a misconfigured admin connection still can't bypass it silently.

Access control

One permission matrix, read by both sides

15 roles across 28 modules

The interface and the server read the exact same permission matrix — there's no separate front-end assumption about what a role can do.

Tested, not just documented

An automated test asserts the client and server copies of the matrix are identical, not just similar, so they can't quietly drift apart.

Segregation of duties

The person who raises a financial document is never the one who can approve it — enforced on the documents that move money, not left to office policy.

Independent quality control

A technician cannot pass their own repair through quality control. That's a system rule, not a suggestion.

Auditability

A trail that can't be quietly edited

Append-only, at the grant level

The audit log rejects UPDATE and DELETE for every database role — including administrators — not just in application logic that could be bypassed.

Soft deletion everywhere else

Operational and financial records are soft-deleted, never hard-removed, so a mistake doesn't erase the trail that would explain it.

Money & compliance

Financial data is structurally protected

Integers, not floating point

Every amount is stored as an integer count of halalas — never a rounded decimal that can drift over thousands of transactions.

Totals computed server-side

A client-supplied total is never trusted; invoice and payment totals are calculated on the server against the source line items.

ZATCA-aligned VAT

Invoicing is built against a configured VAT rate to align with ZATCA e-invoicing requirements, not bolted on as a manual step.

Authentication

Passwords are hashed with Argon2; JSON Web Tokens require a real secret in production — the process refuses to start on a guessable default rather than run insecurely.

Where we're honest about gaps. Not every relationship in the data model is backed by a database foreign-key constraint today — some are naming-convention links, which is a known trade-off we track rather than hide. And roughly two-thirds of the product's screens are still connected to representative fixture data rather than exchanging live traffic with the API under production conditions in a customer's environment. We'll tell you exactly which parts of your workflow are furthest along when we scope a deployment with you.
